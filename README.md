# Scribe

Транскрипция и диаризация аудио, целиком на своём железе. Веб-интерфейс
открывается с любой машины в локальной сети, интернет после установки
не нужен.

- **Загрузка файлов** — полный разбор записи: текст, пословные тайминги,
  разметка по говорящим.
- **Живая запись** — микрофон в браузере, текст появляется по ходу речи.
  После остановки запись автоматически переобрабатывается крупной моделью,
  и черновик заменяется чистовиком.
- **Редактор** — волна, лента говорящих, клик по слову перематывает
  звук, правка текста, переименование говорящих.
- **Выгрузка** — TXT, Markdown, SRT, WebVTT, JSON, DOCX.

---

## Что нужно

| | |
|---|---|
| ОС | Windows 11 с WSL2 (или любой Linux) |
| Docker | Docker Desktop с включённой интеграцией WSL2 |
| Видеокарта | NVIDIA, 8 ГБ VRAM и больше; драйвер от 570 для RTX 50xx |
| Место на диске | ~30 ГБ: образы и веса моделей |
| Интернет | только на время установки |

Без видеокарты сервис тоже запустится, но распознавание пойдёт на
процессоре и будет медленнее в десятки раз.

## Установка

### 1. Проверить окружение

```bash
powershell -ExecutionPolicy Bypass -File scripts\setup_windows.ps1
```

Скрипт посмотрит Docker, WSL2, проброс видеокарты в контейнер, создаст
`.env` из шаблона и, если запущен от администратора, добавит правило
брандмауэра на порты 80 и 443.

### 2. Вписать токен Hugging Face

Модели диаризации закрыты лицензией: нужно один раз открыть
[pyannote/speaker-diarization-community-1](https://huggingface.co/pyannote/speaker-diarization-community-1),
нажать Agree и положить свой токен в `.env`:

```
HF_TOKEN=hf_...
```

Токен используется только при скачивании весов. Дальше он не нужен.

### 3. Собрать образы

```bash
docker compose build
```

Первая сборка долгая: тянется CUDA-базис и PyTorch, суммарно порядка
15–20 ГБ.

### 4. Скачать модели

Сначала поднимите сервис с языковой моделью — скрипт попросит его скачать
модель для полировки чистовика:

```bash
docker compose up -d llm
```

```bash
docker compose run --rm -e HF_HUB_OFFLINE=0 -v ./scripts:/scripts worker-batch python /scripts/prefetch_models.py
docker compose run --rm -e HF_HUB_OFFLINE=0 -v ./scripts:/scripts worker-live python /scripts/prefetch_models.py
```

Веса лягут в `./models`, языковая модель (около 5 ГБ) — в
`./models/ollama`. После этого в `.env` уже стоит
`HF_HUB_OFFLINE=1`, и сервис в сеть не ходит вообще.

Если скачивание языковой модели падает с `TLS handshake timeout` — у
Ollama короткий предел на установку защищённого соединения, и на
медленном канале он не успевает, — скачайте файл модели сами и соберите
её из него. `curl` на таком канале справляется:

```bash
curl -fL -C - --retry 10 -o models/gguf/Qwen3-8B-Q4_K_M.gguf https://huggingface.co/Qwen/Qwen3-8B-GGUF/resolve/main/Qwen3-8B-Q4_K_M.gguf
```

```bash
docker compose exec llm sh -c 'echo "FROM /models/gguf/Qwen3-8B-Q4_K_M.gguf" > /tmp/Modelfile && ollama create qwen3:8b -f /tmp/Modelfile'
```

### 5. Выпустить сертификат

```bash
powershell -ExecutionPolicy Bypass -File scripts\setup_tls.ps1
```

Это не формальность. Браузер отдаёт микрофон только на защищённом
соединении: по `http://192.168.x.x` живая запись не заработает никогда —
так устроен браузер, а не сервис. Скрипт поднимает локальный
удостоверяющий центр через `mkcert` и печатает, что сделать на других
компьютерах сети.

### 6. Запустить

```bash
docker compose up -d
```

Открыть `https://scribe.local` или `https://<адрес-этой-машины>`.

---

## Доступ с других компьютеров

На каждой машине, с которой будут **записывать**, нужно один раз:

1. Установить корневой сертификат `rootCA.pem` — путь печатает
   `setup_tls.ps1`.
2. Добавить строку в файл hosts:
   `192.168.х.х  scribe.local`
   (`C:\Windows\System32\drivers\etc\hosts` или `/etc/hosts`).

Чтобы просто **читать** готовые транскрипты, сертификат не обязателен —
можно открыть по адресу и согласиться с предупреждением. Микрофона при
этом не будет.

## Как устроено

```
                          LAN (без интернета)
 браузер ──── HTTPS / WSS ────► Caddy :443
   микрофон                       │
   webm/opus, куски по 200 мс     ├── /            статика интерфейса
                                  ├── /api/*       backend (FastAPI + SQLite)
                                  └── /ws/live     worker-live

 worker-batch ◄── очередь заданий в SQLite ──► backend
   ffmpeg → faster-whisper → pyannote → слияние
```

| Сервис | Что делает |
|---|---|
| `web` | Caddy: TLS, статика, проксирование |
| `backend` | REST API, SQLite, очередь заданий, экспорт |
| `worker-batch` | Полный разбор файла: ASR, диаризация, слияние |
| `worker-live` | WebSocket, стриминговое распознавание |

Три Python-сервиса разведены по контейнерам намеренно: живой режим
стоит на NeMo 3 (Streaming Sortformer), batch — на `pyannote.audio 4.x`,
и их зависимости не уживаются в одном окружении. Разные образы решают
это без ручной борьбы с резолвером.

БД лежит в именованном docker-томе, а не в bind-mount на диск Windows:
SQLite поверх virtiofs периодически ловит ошибки блокировок. Аудио и
модели, наоборот, в обычных папках — их удобно видеть и бэкапить.

Единственный процесс, который пишет в базу, — `backend`. Воркеры ходят
к нему по HTTP, поэтому конкурентной записи между контейнерами не
возникает в принципе.

### Живая диаризация

Движок — **NVIDIA Streaming Sortformer** (`LIVE_DIARIZATION=sortformer`,
модель `nvidia/diar_streaming_sortformer_4spk-v2.1`, задержка 0,32 с).
Это сквозная потоковая модель 2025 года: звук идёт порциями, а голоса
говорящих держатся в кеше в порядке появления. Её рекомендует и сам
WhisperLiveKit. До неё стоял diart — онлайн-кластеризация эмбеддингов
2021 года.

Выбор сделан по замеру (`bench/eval_live.py compare`, подробнее в
`bench/README.md`). Две опоры: семь записей из библиотеки, где эталоном
служит чистовик, и три встречи корпуса AMI, размеченные людьми:

| | Слов под чужим именем | Путаница говорящих на AMI | Запись втроём | Задержка |
|---|---|---|---|---|
| diart, как было | 26,3% | 14,4% | 36,2% | 0,5 с |
| diart после настройки | 16,0% | 10,0% | 35,3% | 0,5 с |
| **Sortformer** | **14,0%** | **3,4%** | **11,2%** | **0,32 с** |

Sortformer лучше и точнее, и отзывчивее. Особенно на разговоре втроём:
diart находил там двоих из троих. Строгий DER на AMI у Sortformer выше
(34,6% против 28,7%), но вся разница — в границах речи и тишины, а в
транскрипте их задаёт распознавание, а не диаризация. Путаница самих
людей у него втрое ниже.

Как устроено. Модель грузится один раз на процесс из локального кеша —
сервис живёт без сети. Настройки порций — из статьи авторов (arXiv
2507.18446): порция 0,24 с и 0,08 с заглядывания вперёд. Штатная обёртка
WhisperLiveKit ставила свои: секундную порцию без заглядывания и
неверный шаг кадра. Поток разбирает `worker-live/sortformer_stream.py`:
NeMo считает признаки по всей записи сразу, а здесь — на скользящем окне
с запасом по краям, и числа совпадают с расчётом по всей записи до шума
float32. Стенд гоняет этот же класс, так что замер переносится на живой
режим один к одному: по кадрам его разметка совпадает с эталонным
потоковым прогоном NeMo на 99,9–100%. Цифры в таблице выше — именно его.

Отзывчивость. Сквозной замер на записи 90 с: разметка отстаёт от
распознанного текста в среднем на 0,12 с (у diart было 0,24 с), самое
большее — на 1,1 с; само распознавание — на 0,09 с. Пока разметка не
покрыла слово, оно висит серой гипотезой, так что эта разница видна
глазу напрямую. Оба значения приходят клиенту в поле `lag` каждого
сообщения с транскриптом.

Второй проход. Следом за быстрым потоком на той же модели идёт медленный —
с запасом 10 с: кто говорит, он видит точнее, потому что уже слышит, кто
продолжил. Он молча перемечает уже показанные отрезки, и реплики старше
~10 секунд поправляются сами (`LIVE_SORTFORMER_REFINE_LATENCY`, 0 —
выключить). Парный сквозной замер на пяти записях: 15,8% слов под чужим
именем вместо 16,8%, начало реплики уходит предыдущему говорящему в 38,5%
смен вместо 50%. Слова в промежутках между отрезками разметки
WhisperLiveKit по-прежнему отдаёт первому говорящему — их второй проход не
лечит.

Ограничения. Не больше четырёх говорящих — остальных разберёт чистовик.
Изредка на разговоре вдвоём появляется лишний «Спикер 3» на пару фраз;
это тоже исправит чистовик. Правило «новый говорящий появляется, только
наговорив N слов» это лечило, но задерживало настоящего второго
собеседника в начале записи — на замере вышло хуже, и оно отброшено.
Модель обучена в основном на английском, но замер выше сделан на русских
записях.

#### Правила черновика

Они не зависят от движка и работают поверх разметки:

- **Говорящий меняется только на начале слова.** Слово на стыке порций
  распознавания приходит двумя кусками, и WhisperLiveKit назначал
  говорящего каждому куску отдельно — выходило «Таноса нед» у одного и
  «ели три» у другого.
- **Решение по реплике** (`LIVE_MIN_TURN_WORDS=4`): подряд идущие реплики
  одного говорящего короче четырёх слов не могут сменить говорящего и
  приклеиваются к предыдущему. Так делают коммерческие потоковые системы.
  Без этого метка дрожала на стыках, и текст рассыпался на обрывки: 432
  реплики вместо 200, из них 140 короче трёх слов. С правилом — 187 и 2.
  Цена — настоящий ответ в пару слов («Да, конечно») попадает к
  собеседнику.
- **Граница по смыслу** (`LIVE_SNAP_WORDS=1`): если граница говорящих
  прошла посреди предложения, а соседнее слово его заканчивает, граница
  переезжает туда — «…Шептать.» / «Надо всегда…» вместо «…Шептать. Надо» /
  «всегда…».
- **Фильтр галлюцинаций — и в черновике, и в чистовике.** На музыке,
  тишине и коротких шумных фразах Whisper выдумывает подписи из титров:
  «Субтитры сделал DimaTorzok», «Субтитры подогнал «Симон»», «Редактор
  субтитров …», а целой фразой — «Продолжение следует...». На замере так
  вышло у 34 коротких команд из 1916 (Golos farfield), а на чистом
  чтении (FLEURS) Whisper дважды дописал подпись в конец настоящей фразы
  — фильтр убрал только её; в чистовиках библиотеки нашлось шесть таких
  строчек. В чистовике слова подписи выбрасываются вместе с таймингами,
  до разметки говорящих. Фразы, которые говорят и по-настоящему
  («Подписывайтесь», «Спасибо за просмотр», «Продолжение следует» внутри
  фразы), не трогаются. Шаблоны — `hallucinations.py`, один и тот же в
  обоих воркерах; проверка — `tests/test_hallucinations.py`.

Регрессионные проверки — `tests/live_sortformer_check.py`,
`tests/live_word_split_check.py` и `tests/live_diarization_check.py`.

Метки в живом режиме всё равно черновые. Точные имена и границы даёт
доводка после остановки.

#### diart

Прежний движок остался в коде (`LIVE_DIARIZATION=diart`), но в образ не
входит: diart 0.9.2 держит numpy ниже 2, а NeMo 3 требует 2. Кто соберёт
образ с ним, получит и его переходники из `engine.py`: своя диаризация
на каждую запись, поток звука без торможения, свой сбор сегментов,
пороги кластеризации по замеру (`LIVE_DIAR_*`). История этих исправлений
— в git.

### Качество диаризации

Настройки диаризации выбраны по замеру, а не на глаз: на трёх встречах
корпуса AMI с эталонной разметкой. Стенд и инструкция — в `bench/`.

| | Слов с неверным говорящим | DER | Говорящих найдено (из 4) |
|---|---|---|---|
| Было | 2,48% | 20,97% | 4 / 4 / 4 |
| Стало | 2,20% | 20,88% | 4 / 4 / 4 |

Два изменения, и работают они только вместе:

- **Сглаживание коротких вставок выключено.** Оно поглощало настоящие
  короткие реплики вроде «угу» и «да» и было хуже на каждой из трёх
  записей. Но заодно оно прятало лишнего говорящего: без него на одной
  встрече снова появлялся пятый человек.
- **Добавлено слияние лишних говорящих.** Обрывок чужого голоса — меньше
  2% речи и голосом похож на кого-то из участников со сходством не ниже
  0,40 — сливается с этим участником. Пороги строгие: мягкий вариант на
  проверке склеил четверых настоящих людей в двоих. Если число
  говорящих указано вручную, правило не применяется.

Проверено и отброшено: порог кластеризации (от 0,50 до 0,70 результат
одинаковый — кластеризация VBx сходится к одному решению), склейка
коротких пауз, обычная разметка с наложениями вместо эксклюзивной
(лучше на одной записи из трёх, хуже на двух).

Большая часть оставшейся ошибки — не перепутанные люди, а наложения:
когда говорят одновременно, транскрипт с одним автором на слово может
назвать только одного. Это ограничение формата, а не настройки.

### Черновик и чистовик

Стриминговая диаризация хуже офлайновой: у неё нет будущего контекста, и
метки говорящих по ходу записи могут переприсваиваться. Поэтому живая
запись даёт черновик, а после остановки та же запись автоматически
уходит в batch-очередь и через пару минут заменяется чистовиком. В
интерфейсе это видно бейджем на карточке.

### Полировка чистовика языковой моделью

Когда чистовик собран, его доводит локальная языковая модель — сервис
`llm` на Ollama, по умолчанию `qwen3:8b`. В живом режиме она не участвует.
Равноценная замена — YandexGPT-5-Lite-8B (`LLM_MODEL`); T-lite-it-2.1
проверена и не подошла: досочиняет факты в кратком содержании.

- **Стыки реплик — выключено по замеру.** Идея была такая: на каждой
  смене говорящего модель по смыслу выбирает, с какого слова на самом деле
  начинается новая реплика, из вариантов не дальше трёх слов. Выдумать
  слово она не может — ответ ограничен JSON-схемой. Но на трёх встречах
  AMI это ухудшило чистовик у всех трёх проверенных моделей (Qwen3-8B,
  YandexGPT-5-Lite-8B, T-lite-it-2.1): 5,57% слов под чужим именем →
  5,74–6,29%. Модели двигают границы охотнее, чем стоит.
  Включается `LLM_FIX_SPEAKERS=true` — например, чтобы проверить другую
  модель на стенде (`bench/eval_llm.py`).
- **Название** — только если оно не тронуто: «Запись ДД.ММ.ГГГГ ЧЧ:ММ» или
  имя загруженного файла. Своё название модель не перезапишет.
- **Краткое содержание** — несколько пунктов над транскриптом.
- **Имена говорящих** — только подсказка («Похоже, это Андрей ·
  принять») и только если имя дословно звучит в разговоре. Вписанное
  вами имя не трогается.

На ваших записях название и краткое содержание готовы за секунды: 3 с на
двухминутный разговор, 33 с на 48-минутный подкаст — длинная запись
пересказывается по частям и сводится.

Всё это надстройка: модель выключена, не скачана или не отвечает —
чистовик уходит как был. Видеопамять модель занимает только на время
доводки и выгружается после двух минут простоя. На RTX 5070 это впритык:
пик за доводку — 11,2 ГБ из 12 (живой воркер, Whisper с pyannote и модель
вместе). Если в это время идут живые записи и места не хватит, Ollama
перенесёт часть слоёв на процессор — полировка станет медленнее, но не
упадёт.

Образ `llm` собирается из релиза Ollama на GitHub, а не скачивается
готовым с Docker Hub: на медленном канале Docker рвёт соединение при
установке TLS, а сборка через `curl` с повторами справляется.

## Настройка

Всё в `.env`, рядом с `docker-compose.yml`. После правки:
`docker compose up -d`.

| Параметр | Смысл |
|---|---|
| `BATCH_ASR_MODEL` | Модель для файлов. `large-v3` — точнее всего для русского |
| `LIVE_ASR_MODEL` | Модель для живой записи. `large-v3-turbo` — компромисс с задержкой |
| `COMPUTE_TYPE` | Точность. **Не меняйте на int8 на RTX 50xx** — см. ниже |
| `LIVE_DIARIZATION` | `sortformer` (по умолчанию), `none` или `diart` — последний только в образе, собранном с ним |
| `LIVE_SORTFORMER_LATENCY` | Задержка живой разметки: `0.32` (по умолчанию) или `1.04` — чуть точнее, на 0,7 с медленнее |
| `VAD_FILTER` | Отсекать тишину до распознавания. **По умолчанию выключено** — см. ниже |
| `LIVE_VAD` | То же для живого режима. Включено: держит задержку |
| `INITIAL_PROMPT` | Словарь по умолчанию: имена и термины через запятую |
| `LLM_MODEL` | Языковая модель для полировки чистовика, по умолчанию `qwen3:8b` |
| `LLM_NOTES`, `LLM_FIX_SPEAKERS` | Название, краткое содержание и подсказки имён — включено; поправка стыков реплик — выключена по замеру |
| `DROP_HALLUCINATIONS` | Выбрасывать из чистовика строчки из титров, которые Whisper выдумывает на тишине. Включено; черновик чистится всегда |
| `NUM_SPEAKERS` | Точное число говорящих, `0` — определять самому |
| `SMOOTH_SPEAKER_TURNS` | Сглаживание коротких вставок. Выключено по замеру — см. «Качество диаризации» |
| `TINY_SPEAKER_MAX_SHARE`, `TINY_SPEAKER_MIN_SIMILARITY` | Пороги слияния лишних говорящих, по умолчанию `0.02` и `0.40` |
| `MAX_LIVE_SESSIONS` | Сколько живых записей одновременно. Упирается в VRAM |
| `AUTO_REFINE_LIVE` | Переобрабатывать живую запись после остановки |
| `RETENTION_DAYS` | Через сколько дней удалять аудио. Транскрипты остаются |

## Если что-то не работает

**Микрофон недоступен, кнопка записи ругается на HTTPS.**
Страница открыта по `http://`. Нужен `https://` и установленный корневой
сертификат — шаг 5 установки.

**`CUBLAS_STATUS_NOT_SUPPORTED` при распознавании.**
На картах RTX 50xx (архитектура Blackwell, sm_120) int8-ядра CTranslate2
не работают. В `.env` должно стоять `COMPUTE_TYPE=float16`.

**Диаризация падает с ошибкой загрузки модели.**
Не принята лицензия на Hugging Face или нет `HF_TOKEN`. Откройте
страницу модели, нажмите Agree, повторите шаг 4.

**Живая запись отвечает «больше видеопамять не позволяет».**
Достигнут лимит `MAX_LIVE_SESSIONS`. Либо дождитесь окончания чужой
записи, либо возьмите модель полегче в `LIVE_ASR_MODEL`.

**Распознаётся меньше половины сказанного, текст без знаков препинания.**
Почти наверняка включён `VAD_FILTER`. Отсечение тишины хорошо работает
только на чистых записях: если под речью играет музыка, шумит комната
или идёт запись созвона, детектор принимает такие куски за тишину и
выбрасывает их до распознавания. На проверочной записи это стоило
больше половины слов — 28 вместо 58 — и заодно пунктуации, потому что
уцелевшие обрывки распознаются вне контекста фразы. Поставьте
`VAD_FILTER=false` (значение по умолчанию) и переобработайте запись
кнопкой «Уточнить». Для живого режима тот же параметр — `LIVE_VAD`.

**Словарь записи: как им пользоваться.**
В форме загрузки и в редакторе есть поле «Словарь» — имена участников,
названия, термины. Оно передаётся модели как `hotwords` и подмешивается
в каждый фрагмент записи, поэтому список должен быть **коротким**: до
200 символов, через запятую. Описание встречи туда писать нельзя — на
проверочной записи абзац на 160 символов вытеснил контекст речи и стоил
трети распознанных слов, причём молча: из транскрипта выпали 25 секунд
подряд. Длиннее предела обрезается автоматически, с записью в лог.

**Обработка встала на «в очереди».**
Посмотрите логи: `docker compose logs -f worker-batch`. Зависшие задания
возвращаются в очередь автоматически через 10 минут.

**`docker compose build` падает с `TLS handshake timeout` при скачивании
базовых образов.**
Проверьте, не поднят ли VPN в режиме TUN (sing-box, Happ, Clash,
ZeroTier). Такие клиенты перехватывают маршруты и ломают трафик
виртуальной машины Docker через адаптер `vEthernet (WSL)`, хотя сам
Windows при этом ходит в сеть нормально. Отличить просто: если

```bash
curl -o /dev/null -w "%{http_code}\n" https://registry-1.docker.io/v2/
```

из Windows отвечает `401`, а `docker pull` в это же время висит, — дело
именно в туннеле. Отключите его на время сборки или разрешите в нём
подсеть WSL.

Если туннель отключить нельзя, а прокси у него есть (Xray, sing-box и
подобные обычно слушают на `127.0.0.1`), образ можно забрать в обход
демона и загрузить файлом:

```bash
py -3 scripts/pull_image.py library/caddy 2-alpine caddy:2-alpine caddy.tar
docker load -i caddy.tar
```

Адрес прокси задаётся переменной `REG_PROXY` (по умолчанию
`http://127.0.0.1:10808`). Скрипт качает манифест и слои напрямую через
прокси, собирает архив и не зависит от внутреннего ретранслятора
Docker Desktop, который в такой конфигурации часто не работает.

## Разработка

```bash
docker compose up -d backend worker-batch worker-live
cd frontend
npm install
npm run dev
```

Vite поднимется на `:5173` и сам проксирует `/api` и `/ws` — адреса в
коде править не нужно. Живая запись в dev-режиме работает, потому что
`localhost` браузер считает защищённым контекстом.

Проверка типов фронтенда: `npm run typecheck`.

### Тесты

```bash
python tests/test_merge.py
python tests/test_backend.py
```

Первый проверяет слияние ASR и диаризации, второй прогоняет всё API на
временной базе. Подробности — в `tests/README.md`.
